작성일 2026-08-26 · 대상 `data/incoming/` (신설) 및 수집 작업 전반

관련 문서. 이 문서는 "무엇을 언제 얼마나 모을 것인가"만 다룬다.

| 문서 | 다루는 것 |
|---|---|
| `지역가이드_수집체크리스트.md` | 파일 작성 규칙 · 항목별 수집처 · 헤더 규격 |
| `행정구역_확인_기록.md` | 행정구역 스크리닝 원칙과 지역별 판정 |
| `지역확장_2단계_실행계획.md` | 반영(통합) 절차 · 게이트 · 평가셋 관리 |

## 0. 기본 구조 — 수집은 자유, 반영은 게이트

```
[수집]  data/incoming/ 에 비축     ← 코드 변경 0 · 아무 때나 main 머지 · 병렬 가능
   ↓  (반영 배치 선정: 3개 안팎)
[재검증] 출처 재방문 · 기준일 갱신   ← 수집이 오래됐을수록 여기서 거른다
   ↓
[반영]  incoming → data/guide 이동  ← 2단계 실행계획의 절차·게이트를 따름
        + regions.py 항목 추가
```

`data/incoming/` 이 안전한 근거: `rag_reindex`(files 모드)와 `seed_docs`(db 모드)
모두 `settings` 의 `LAWS_DIR`·`GUIDE_DIR`·`DOCS_DIR` 세 폴더만 **비재귀로** 읽는다.
incoming 은 어느 모드에서도 색인되지 않으므로, 미완성 파일이 main 에 있어도
챗봇 답변에 섞이지 않는다. (수집체크리스트 원칙 ②의 "초안은 guide 밖에" 를
폴더 하나로 제도화한 것이다. `_` 프리픽스는 files 모드에서 안 걸러지므로 쓰지 않는다.)

**incoming 안의 파일도 처음부터 최종 규격으로 쓴다** — 파일명, 첫 줄 제목,
출처 헤더, 섹션 마커 전부. 그래야 반영이 "파일 이동"으로 끝난다.
규격은 수집체크리스트 3절을 따른다.

## 1. 수집대장 — 상태는 세 단계뿐

이 문서 하단 표가 수집대장이다. PR 마다 갱신한다.

| 상태 | 뜻 | 올리는 사람 |
|---|---|---|
| 수집됨 | incoming 에 파일 존재, 형식 검사 통과 | 수집자 |
| 검증됨 | 다른 사람이 출처 교차확인 완료 | 검증자 (수집자와 다른 사람) |
| 반영됨 | data/guide 이동 + 게이트 통과 | 반영 배치 담당 |

- 수집자와 검증자는 반드시 다른 사람이다. robots.txt 로 원문 확인이 막혔던
  항목(검색 요약으로만 확인한 것)은 검증자가 **다른 경로**(조례 원문 elis.go.kr,
  콜센터 전화)로 확인하고 확인 경로를 대장에 남긴다.
- 평가 문항 출제는 반영 시점에, **수집자·검증자가 아닌 제3자**가 한다
  (2단계 실행계획의 규칙과 동일).

## 2. 후보 풀과 우선순위

선정 기준은 2단계 실행계획 "광역 후보 고르는 기준" ①~④에 하나를 더한 다섯 개다:
① 단일 배출체계 성립 ② 이름 충돌 없음 ③ 자료 접근성 ④ 팀 연고 **⑤ 행정 안정성**.

모든 후보는 수집 착수 전에 행정구역 스크리닝 3문항(존재하는가 / 통합·분리
논의 중인가 / 단일 체계 범위인가)을 통과해야 하며, 결과를
`행정구역_확인_기록.md` 에 한 줄이라도 남긴다. 아래 분류는 2026-08-27 기준이며
근거는 `행정구역_스냅샷_2026-08-27.md` 에 있다. **착수 시점에 재확인**한다.

### 1순위 — 충돌 없고 접근성 좋은 곳부터

| 후보 | 메모 |
|---|---|
| 대구 | 존속 확정(민선 9기 시장 취임으로 증빙). 반영 시 `q027` 을 다른 미보유 지역으로 교체 필요 — 수집 자체는 무관. **2026-08-27 수집 완료** |
| 창원 | 특례시. 기존 키와 충돌 없음 |
| 청주 · 전주 | 도청 소재 중견시. 충돌 없음 |
| 경기 남부 대도시 (성남·용인·부천 중 접근성 좋은 곳) | 수원과 같은 권역이라 수집 노하우 재사용. 분도 추진안에서 남부는 '경기도'로 유지 |
| 고양 | ⚠️ 분도 추진안의 **북부 11개 시군에 포함** — 초판의 "남부라 무관" 분류는 오류였음. 후보 유지하되 플래그, 성남·용인 뒤로 |

### 2순위 — 반영에 선행 조건이 있는 곳 (수집은 가능)

| 후보 | 선행 조건 |
|---|---|
| 부산 타 구 (해운대구 등) | 별칭 설계 신중히. regions.py 가 긴 별칭 우선 매칭이라 가능해졌지만, 반영 전 `verify_regions.py` 로 충돌 0건 확인 필수 |
| 인천 타 구 | 위와 동일 |
| 경기 광주시 | "광주" 별칭이 옛 광주광역시 표기·통합시와 얽힌다. 별칭을 "경기광주"·"광주시"로 좁게 설계 |

### 보류 — 수집하지 않는다

| 대상 | 이유 · 재검토 조건 |
|---|---|
| 전남광주통합특별시 | 단일 체계 불성립 + 과도기(행정구역_확인_기록의 판정 유지). 조례 정비가 안정된 뒤 권역 분할 방식으로 재검토 |
| 도 단위 (경기·강원 등) | 시·군마다 갈려 한 코드로 못 묶는다 (2단계 실행계획의 비권장 판정) |

### 미보유 지역 문항용 예약

`no_answer` 지역 문항은 **미보유 지역**이 정답 재료다. 현재 `q027`(대구 수성구),
교체 후보로 춘천이 거론돼 있다. **문항에 쓰는 지역을 수집 후보에 넣으면 문항을
또 교체해야 하므로**, 문항용 지역 1~2곳(예: 춘천)은 수집 대상에서 빼두고
대장에 "문항 예약"으로 표시한다.

## 3. 지역 1개당 수집 절차

1. **스크리닝** — 행정구역 3문항 확인, 기록 남김. 탈락이면 대장에 사유와 함께 종결.
2. **접근성 사전조사 (15분)** — 시 차원 통합 분리배출 안내 페이지가 있는지,
   robots.txt 로 막히는지 훑는다. 막히는 항목이 많으면 우선순위를 내리고
   다음 후보로 넘어간다. 수집이 싸다는 전제는 접근성이 좋을 때만 성립한다.
3. **수집** — 섹션 구성은 확정안 그대로: 배출 요일·시간 / 품목별 요령 / 음식물 /
   대형폐기물 / 유해폐기물 / 문의. 항목별 수집처는 수집체크리스트 2절.
   공통 가이드와 겹치는 서술은 쓰지 않는다(지역 문서 자리는 2청크뿐).
4. **작성** — 최종 규격으로 incoming 에 저장. 파일명과 제목 **양쪽에** 지역
   키워드. 분량은 기존 신규 지역 수준(청크 13~18, 대략 4.5~6.5KB)으로 누른다.
5. **미확인 항목 처리** — 공식 출처를 못 찾은 항목은 추측으로 채우지 말고
   통째로 뺀다(울산 폐의약품 전례). 뺀 목록을 대장에 남겨야 검증자가
   이어받을 수 있다.
6. **형식 검사** — `python check_guide_format.py data/incoming` 오류 0건.
7. **PR** — 지역 1개 = PR 1개. 대장 상태를 "수집됨"으로 갱신.
   서로 다른 파일만 만지므로 수집 PR 은 리뷰 후 바로 머지해도 된다.

## 4. 재검증 — 비축분에는 유통기한이 있다

반영 배치에 넣기 직전, 검증자가 파일 헤더의 출처 URL 을 재방문해 세 가지만 본다.

1. **행정구역** — 통합·분리 상태 변동 (특히 대전은 재점화 리스크로 상시 플래그)
2. **요일·시간** — 조례 개정으로 가장 자주 바뀌는 항목
3. **수수료·신고 채널** — 대형폐기물 위탁업체 변경 여부

변동이 있으면 고치고 작성 기준일을 갱신, 없으면 기준일만 갱신한다.
**작성 기준일에서 8주가 지난 파일은 재검증 없이 반영하지 않는다.**
출처 URL 이 헤더에 있으면 이 작업은 지역당 30분이면 끝난다 — 없으면
수집을 다시 하는 것과 같으므로, 헤더 규격을 지키는 것이 이 전략의 전제다.

## 5. 반영 배치 선정 기준

배치는 3개 안팎으로 묶고, 이후는 2단계 실행계획의 절차(코드 변경 · 게이트 ·
평가셋)를 따른다. 무엇을 먼저 넣을지는 아래 순서로 거른다.

1. 미확인 항목이 적은 것 (출처 완결성)
2. 행정구역이 안정된 것 (플래그 없는 것 우선)
3. 시연 스토리 — 광역시·특례시·중견시가 섞이면 "확장 가능성" 서사가 선다
4. 평가에서 흔들리면 배치에서 빼고 다음 후보로 교체 — 비축분이 있기에
   가능한 선택지이며, 이 전략의 존재 이유다.
